# ADR-0010: Atomic local repository command integrity

Status: **ACCEPTED — bounded contract and synthetic proof** · Date: 2026-10-05 · Phase: 1C

## Context

ADR-0003 requires revision-safe local transactions and a deletion fence. Phase 1C needs observable application contracts before a real persistence adapter or production learner schema. Lost responses, concurrent writers and pending commands after deletion must not corrupt or resurrect state.

## Decision

Use a small typed generic async atomic-record port with an exact runtime codec. Version the command and receipt envelopes separately from the record schema and replay. Use record-local nonnegative safe-integer revision, global non-identifying safe-integer storage epoch, and caller-supplied opaque operation ID. Inputs/outputs obey the existing bounded canonical-data rules; codecs preserve canonical wire identity without hidden normalization or migration.

Process validation, current epoch, success receipt and then expected revision in that order. Identical same-epoch retries return the original receipt with no new mutation; global same-ID/different-command reuse conflicts. Failed commands create no receipts and leave all state unchanged. Explicit create requires an absent record and starts at revision 1; update cannot create missing records. State-changing writes advance revision once, with overflow rejected before commit.

Delete preflights revision and global epoch advancement, removes the target and clears old-epoch receipts atomically. Survivor data/revisions remain intact but old sessions cannot write. A delete response is a receipt only for that call; the old-epoch retry requires reload/reconciliation. No tombstones are retained. Full clear and production profile-ID reuse are deferred, and future imports must preserve the destination fence rather than restore source control metadata.

## Alternatives

A concrete minimal learner aggregate would prematurely select the production data schema; a generic port with a typed synthetic record proves integrity independently of educational behavior. Last-write-wins loses evidence, upsert permits resurrection, dedupe-before-epoch permits stale success, and per-profile epochs do not implement the accepted global safety fence. Clock/UUID generation, hashes, leases and BroadcastChannel add no necessary integrity proof here. Failure journaling complicates retry behavior without a current need.

## Consequences and limits

Adapters must commit payload, revision and success receipt together inside their real transaction, check epoch/revision in that transaction, and run the reusable conformance suite plus adapter-specific abort/crash/device tests. Independent synthetic sequence tests and actual defect mutations establish local port evidence; a one-step memory state replacement does not prove browser durability or cross-process transaction behavior.

Canonical fingerprints may contain data and remain internal; public receipts/errors omit histories and personal diagnostics. The fake retains synthetic success receipts only for its test lifetime until epoch rotation, with no production pruning policy. Retention, learner schema, adaptation, real storage, backup/import, UI, localisation/speech and offline decisions remain separate gates. ADR-0006/0007 and D29/D30 remain proposed.

## Reversal conditions

Change integrity semantics only through explicit review and applicable new version IDs. A future adapter may propose a different opaque epoch representation with an ADR and conformance proof; it cannot weaken the global stale-write fence. Real-data use still requires unresolved privacy/retention decisions.
