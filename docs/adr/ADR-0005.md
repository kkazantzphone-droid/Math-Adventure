# ADR-0005: Localisation and speech abstraction

Status: **ACCEPTED** · Date: 2026-10-04 · Phase: 0 (specification only)

## Context

Reading independence and Greek/English/German initial operation require contextual language and speech, while future languages must not modify math logic.

## Decision

Use exact el-GR/en-GB/de-DE V1 targets with fr-FR/es-ES/it-IT/pt-PT architecture, independent UI/instruction/number-speech settings, reviewed complete messages and a SpeechService port. V1 explicitly selects local exposed voices; no silent remote/default/pt-BR fallback. Missing speech degrades visibly. Official packs require two reviews including exact-regional native participation.

Semantic utterance plans must eventually express squared/cubed/general powers, roots, perimeter/area/units and angle/spatial concepts naturally in each exact supported locale. MathML or a typesetter cannot substitute for reviewed wording or guarantee seven-locale speech. No advanced translations/typesetter are implemented in Phase0.

## Alternatives considered

English strings in domain, naïve word concatenation and direct UI SpeechSynthesis calls mix concerns. Paid/cloud TTS and microphone input add privacy/network dependencies. Prerecorded/local native providers remain possible later.

## Consequences

One semantic task can have several renderings/utterances. Provider capability/status, selected-locale assets and parent Voice Check are required. No seven-locale offline guarantee.

## Risks

Voice list delays, OS-versus-browser exposure, pronunciation differences, mixed-language context, stale offline tests and asset licenses.

## Reversal conditions

Provider changes must pass same contracts/privacy/device tests. Remote TTS or voice input requires a new ADR/privacy review; locale additions require reviewed pack data, not math rewrites.
