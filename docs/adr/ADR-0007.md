# ADR-0007: Offline/service-worker strategy

Status: **ACCEPTED — bounded Phase 1E shell** · Proposed: 2026-10-04 · Accepted: 2026-10-06

## Context

The cached application shell must survive disconnection. Installation alone is
insufficient: partial downloads and mid-session activation can mix releases.
The owner conditionally authorized acceptance under D44 only after genuine
production lifecycle evidence. Independent native Chromium root/subpath and
fresh-tree proofs now satisfy that condition; the [completion report](../PHASE_1E_COMPLETION_REPORT.md)
records the candidate, repairs and limits.

## Decision

Use a browser-standard worker and small existing pinned-Vite build hook, with no
new package. Generate a complete same-origin essential declaration with exact
bytes/hashes. Shell and worker behavior determine immutable release identities;
shell compatibility metadata is separate from mathematical replay and future
learner schema versions. Local manifest/icon and bundled draft locale resources
belong to the coherent shell.

Install the complete release atomically. A failed essential response cannot become
ready and preserves the existing working release. Serve only verified declared
resources from their own release; admit no cross-origin/runtime/learner-dependent
cache entries. Names and bounded ownership metadata contain release/schema/scope
information only. Offline shell readiness is separate from optional speech and
future learner saving.

Leave updates waiting, with no install-time automatic skipWaiting. Require an
explicit Home request and bounded native all-client prepare/freeze/commit rounds.
Missing, unready or newly discovered clients block activation; superseded workers
cancel before the irreversible boundary. Recovery reloads only acknowledged
clients and verifies each new document's shell marker. Stale retirement waits for
all current clients, targets only canonical prior-owned releases and stops while
another candidate is staged. Native release-specific Web Locks coordinate cache
handle acquisition and paired retirement; unavailable coordination fails closed.

This decision accepts the observed shell lifecycle only. Learner persistence,
migrations, retention, backup/import, hosting and broader device support remain
unimplemented or separately gated. It does not accept the fuller future
learner-data protocol in the offline specification.

## Alternatives considered

InjectManifest/Workbox assists compilation/precache generation but still needs the
custom all-tab readiness/recovery policy and adds dependency maintenance. The
[tool comparison](../PHASE_1E_OFFLINE_DESIGN.md) selects the smaller dependency
surface for this bounded shell. Generated automatic policy does not prove a safe
client boundary. CDN essentials and provider-specific runtime APIs are unnecessary.

## Consequences

Online first installation and discovery use network. Required cached application
resources were delivered offline with native worker provenance and independent
body hashes. The proof combines browser offline mode with an owned loopback
transport gate because automatic worker checks bypassed offline emulation.
This mechanism is not physical disconnection or universal device-network isolation.
Old resources may remain while a client cannot recover; retention favors safety
over early reclamation. Quota/eviction and future origin/data migration need their
own proofs. No production hosting is selected or deployed.

## Risks

Eviction/quota, blocking/unresponsive tabs, same-origin compromise and offline users
unable to receive fixes remain risks. Native client discovery is not a browser-wide
atomic transaction. Proof covers installed Chrome 154.0.8037.58 at root and
`/math-adventure/` in separate synthetic contexts. Installed-PWA UI, device/browser
cold restart, other browsers, overlapping scopes, assistive technology, public-host
headers and offline speech are not certified.

## Reversal conditions

Revise the worker/tool strategy if required coherence, safe activation or supported
platform evidence fails; preserve usable cached releases and the explicit safe
boundary. Future learner/device/hosting changes require their own authorized
decision and lifecycle proof. Desktop packaging remains separately scoped.
