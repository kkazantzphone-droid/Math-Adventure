# ADR-0002: Domain/application/UI dependency boundaries

Status: **ACCEPTED** · Date: 2026-10-04 · Phase: 0 (specification only)

## Context

Mathematical truth must survive changes of language, UI framework, browser and future packaging. Contributor clarity matters more than speculative package infrastructure.

## Decision

Use pure domain math/puzzles/learning/game modules; application orchestration and ports; presentation/localisation; infrastructure adapters; React UI and a composition root. Domain imports no React, DOM, IndexedDB, service worker, speech or Tauri APIs. UI calls commands/view models, not concrete adapters. Start with one repo and enforce imports.

Geometry/spatial reasoning, measurement and powers/roots are first-class domain semantics alongside the other pathways. SVG/HTML/MathML or later typesetting are replaceable presentation adapters; domain truth/evidence never depends on pixels, markup or spoken symbols. Canonical concepts can cross domain views without a global level.

## Alternatives considered

All-in-component logic mixes truth/state/UI. Independent workspace packages add overhead without a second consumer. A large state framework or runtime plugin system is premature.

## Consequences

Domain tests run without a browser; concrete adapters are replaceable. Need explicit value/event/port contracts and import restrictions during Phase1.

## Risks

Rules can erode through shared utilities or duplicate UI calculations; compile/lint tests must enforce direction and transactions.

## Reversal conditions

Extract packages or revise layers when a real second consumer or measured import/build problem justifies it; preserve pure truth/evidence boundaries.
